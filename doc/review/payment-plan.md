# 漫展约拍小程序微信支付实施方案与决策清单

> 供产品/运营/开发拍板；基于 `payment-wxpay-research.md`、`payment-test-strategy.md`、`payment-integration-design.md`。本文件是实施建议，不代表资质、退款规则或现价单位已经确认。金额和支付接口均以“分”为单位。

## 1. 一页结论

### 能不能做

可以做，建议采用**普通商户直连的小程序支付**：小程序调用 `wx.requestPayment`，后端用微信支付 API v3 JSAPI 下单。需有完成认证且适用摄影服务类目的小程序主体、可申请普通商户号的经营主体、已开通 JSAPI/小程序支付并与 AppID 绑定的商户号，以及公网 HTTPS 回调域名。个人主体不能开通普通商户直连；当前资格待核实。

目前项目已有微信登录及预约 API，但没有支付表、微信支付 API、支付回调、退款、对账或 `wx.requestPayment`。既有预约状态只能表示履约，新增独立资金状态，不把“已支付/已退款”塞进 booking 状态。

### 工期建议

- **最小可用（建议首发）**：约 8-12 个开发人日；1 名后端 + 1 名前端可并行，约 1.5-2.5 周日历时间。包括固定价/已接受报价全额预付、支付/退款回调、查单关单、基本管理退款操作、自动化 mock 测试和真机小额验收；不含商户号审核等待。
- **完整首期**：约 15-22 个开发人日；约 3-5 周日历时间。增加 T+1 交易/资金账单导入、差异列表与处理、异常退款补偿、管理端审计/告警和连续灰度观察。
- 商户号开户/微信审核等待按 1-5 天预留（实际待验证，可与开发并行）；真实联调和 0.01 元验收约 1-2 个工作日。此处是工程估算，不是承诺排期；未知金额单位、主体资质、退款规则会改变工期。

### 现在需要用户提供

1. 小程序 AppID、认证主体类型，以及是否有同主体普通商户号和 JSAPI 权限；密钥仅通过安全配置渠道，不写进聊天或代码库。
2. 收款主体是否为平台、平台与摄影师的收入结算安排；商户主体与小程序主体的关系/绑定状态。
3. `bookings.total_price` 与 `quote_price` 的现行单位和两三个真实样例（例如数据库值 399 表示 399 元还是 399 分）。
4. 固定价和面议是否都全额预付；摄影师拒绝、用户取消、管理员取消各时点退款规则。
5. 未支付支付窗口、现有 H-8 待确认超时的业务含义，以及是否首发接 T+1 对账。
6. 后端生产 HTTPS 域名、支付/退款回调可达性和负责真实小额验收的微信号/真机。

### 主要风险

- 主体/类目/商户号/AppID 绑定未通过，真实交易无法验收；v3 无公开沙箱，v2 沙箱不支持 JSAPI。
- 现价单位未确认会导致实收金额放大或缩小；必须先核对数据库样本并只在边界转换为整数分。
- 已支付取消、微信回调与超时关单并发若处理不当会造成“已扣款但预约取消/丢回调”；需数据库事务、行锁、幂等和退款补偿。
- 全额预付及退款政策会影响消费者体验、商户售后责任和结算；不能由工程实现自行推定为已拍板。
- `PAYMENT_ENABLED` / `WX_PAY_ENABLED` 名称需统一；建议代码与部署只保留一个正式键 `WX_PAY_ENABLED`，产品文档中把它称为支付总开关。

## 2. 方案对比

| 项目 | 最小可用（建议先做） | 完整首期 |
|---|---|---|
| 交易范围 | 固定价 + 已接受面议，全额预付；互勉不支付 | 同左 |
| 资金数据 | `payment_orders`、`payment_refunds`、通知去重、outbox；booking 仍只表示履约 | 同左，另加 `reconciliation_runs/items` 或等价账单导入/差异记录 |
| 退款 | 用户/摄影师/管理员取消进入统一退款流；管理端可发起/查询；退款通知与查退款 | 增加部分退款工作流、异常退款队列、操作审核、财务差异处理和报表 |
| 对账 | 先有本地账务查询/导出与人工商户平台核对；不自动导入账单 | 每日 T+1 交易及资金账单导入、hash 校验、幂等重导、差异报告和告警 |
| 自动化 | mock provider + 真格式自签回调 + PostgreSQL 并发/幂等测试 | 再覆盖账单模拟、对账差异修复流程与运维告警 |
| 估算 | 8-12 开发人日，约 1.5-2.5 周并行历时 | 15-22 开发人日，约 3-5 周并行历时 |
| 代价/取舍 | 上线初期需人工核对账单；退款异常由后台人工处理 | 开发及运营流程更多，但财务可追溯性、差异发现和扩展性更好 |

**建议**：先完成最小可用并把账单下载/解析接口边界留好；若首月交易量或财务要求较高，则在开真实支付前完成完整对账，不要把“人工对账”长期当自动化替代。

## 3. 实施步骤与验收

以下路径基于现有仓库；文件清单是计划改动范围，尚未实现。迁移编号按当前最高 `000032` 顺延为 `000033`，实施前再次检查迁移目录最高编号。

### 阶段 0：资质与业务规则冻结（用户/运营，1-5 天审批可并行）

**准备**：认证小程序主体及摄影服务类目；普通商户号和小程序支付权限；将 AppID 绑定商户号；准备商户 API 私钥/证书序列号、APIv3 密钥、微信支付公钥及公钥 ID；准备公网 HTTPS 支付与退款通知 URL。

**计划涉及**：商户平台/公众平台配置，不改代码。配置项计划在 `comic/server/internal/config/config.go`：`WX_PAY_ENABLED`、`WX_PAY_MCHID`、证书序列号、私钥挂载路径、APIv3 密钥、微信支付公钥路径及 ID、支付/退款 notify URL。

**验收断言**：AppID 与 mchid 绑定且可调用小程序/JSAPI 支付；回调 URL 公网 HTTPS 可达；密钥可由服务进程读取但不在 Git、镜像、小程序包或日志中；商品/服务、收款主体、取消退款规则对用户可见。任一资质未满足时只做 mock，不开启真实入口。

### 阶段 1：后端数据与下单/回调（约 4-6 开发人日）

**计划改动文件**：
- 新增 `comic/server/migrations/000033_payment_orders.up.sql`、`.down.sql`。
- 新增 `comic/server/internal/repository/payment_orders.sql.go`、`payment_refunds.sql.go`、`wechat_notifications.sql.go`、`payment_outbox.sql.go`（按仓库生成约定调整）。
- 新增 `comic/server/internal/service/payment_service.go`、支付 provider/微信实现。
- 新增 `comic/server/internal/handler/payment_handler.go`。
- 修改 `comic/server/internal/config/config.go`、`comic/server/cmd/api/main.go`。

**接口草案**：
- `POST /api/v1/bookings/:id/payments`：当前 coser 发起/复用预支付，服务端按订单快照算分、取当前用户同 AppID 的 openid，响应小程序二次签名五元组。
- `GET /api/v1/payments/:outTradeNo`：付款人查询本地资金状态。
- `POST /api/v1/payments/wechat/notify`：验签、解密、核对、幂等入账；无用户登录中间件。
- `POST /api/v1/payments/wechat/refund-notify`：退款通知处理。
- 微信侧调用 `/v3/pay/transactions/jsapi`；查单 `/v3/pay/transactions/out-trade-no/{out_trade_no}?mchid=...`；关单 `/v3/pay/transactions/out-trade-no/{out_trade_no}/close`。

**验收断言**：重复创建同一预约复用同一 `out_trade_no`；金额由服务端读库并用分整数，0 金额互勉不可下单；签名应答验证通过；正确回调只入账一次；错签名/错 serial/解密失败/AppID/mchid/openid/金额不符均不改变资金/预约状态；数据库失败返回非 2xx；通知事务提交后应答成功。

### 阶段 2：预约状态机与退款（约 3-4 开发人日）

**计划改动文件**：
- 修改 `comic/server/internal/service/booking_service.go`：取消、完成、摄影师拒绝、报价接受和管理员取消统一经过支付域规则。
- 修改 `comic/server/internal/repository/bookings.sql.go`：条件更新/行锁查询；禁止旧的无条件读判写覆盖支付结果。
- 修改 `comic/server/internal/service/admin_manage_service.go`（管理员取消入口复用统一服务）。
- 新增 `comic/server/internal/service/payment_service_test.go`、`payment_concurrency_test.go` 和 PostgreSQL 集成测试。

**规则**：固定价 `pending` 支付成功后自动 `confirmed`；面议必须 `price_status=agreed` 才能支付（报价接受已置 `confirmed`）；互勉不支付；收费订单未支付不能完成。未支付超时先查单再关单并取消；H-8 超时复用同一过期协调器，已支付不得被超时取消。已支付取消/摄影师拒绝自动创建退款申请，默认建议全额退款，最终仍以退款通知/查退款确认。

**接口草案**：`POST /api/admin/v1/payments/:outTradeNo/refunds`（管理员发起/复核退款）；退款实际通过 `/v3/refund/domestic/refunds`，最终状态由退款通知或查退款决定。

**验收断言**：并发回调/取消/关单/完成均不丢支付事实；同一通知并发 20 次仅一个支付状态迁移和 outbox 事件；支付成功后取消留下支付 SUCCESS + 退款处理中，退款成功前不显示“已退款”；退款累计（成功+处理中）不超过实付金额；条件更新不匹配返回 409。

### 阶段 3：前端 `requestPayment`（约 1-2 开发人日）

**计划改动文件**：
- 修改 `comic/src/api/index.ts`（若现有 API 导出集中于此）或新增支付 API 方法。
- 修改 `comic/src/pages/order/detail.vue`、`comic/src/pages/order/list.vue`：待支付操作、支付状态刷新和结果展示。
- 修改 `comic/src/types/index.ts`：支付/退款 DTO。

**接口调用**：前端先 `POST /api/v1/bookings/:id/payments`，再用返回的 `timeStamp/nonceStr/package/signType/paySign` 调用 `uni.requestPayment`/微信小程序 `wx.requestPayment`；无论成功、失败或用户取消，都刷新 `GET /api/v1/payments/:outTradeNo`，不能以前端 success callback 当作收款凭据。

**验收断言**：连点按钮防抖且后端幂等；客户端传入的 amount/openid 不被信任；取消/失败不伪造支付成功；成功后以服务端状态展示；面议未达成价格、互勉订单不出现付款入口。模拟模式使用独立模拟收银台，不请求真实微信收银台。

### 阶段 4：自动化测试与真机验收（约 2-3 开发人日，真实联调 1-2 天）

**计划改动文件**：新增 `comic/server/internal/payment/mockpay` 或 `comic/server/internal/payment/mockpay.go`、支付服务单测/集成测试、前端支付流程测试（若现有测试设施可用）。具体测试框架待验证；并发和唯一索引测试须用 PostgreSQL，不仅 mock repository。

**本地验收**：mock gateway 生成真格式自签回调，生产验签/解密/幂等处理代码保持共用；小程序开发者工具用模拟收银台，不尝试依赖其弹真实支付窗。覆盖下单重试、金额篡改、错签名/错密钥、重复与乱序通知、取消/支付竞态、超时关单、部分/超额退款、对账 CSV 差异。mock/confirm 只在测试构建或严格非生产环境可达，生产启动自检必须证明其为 404。

**必须真商户号+真机人工验收**：iOS/Android 真机各一次 0.01 元支付；支付通知重试/查单补偿；至少一笔 0.01 元退款并确认微信账单/零钱实际到账；核对 AppID/mchid 绑定和真实回调域名；下载真实 T+1 账单（若选择完整方案）。开发者工具不能证明真实收银台、真实微信回调、退款到账或账单格式。

**验收断言**：本地核心业务用例及 Go `go test -race ./...`、PostgreSQL 并发集成测试通过；真实真机支付/退款结果与商户平台一致；生产 mock 入口不可用。

### 阶段 5：灰度与上线（约 1-2 开发人日，观察窗口另计）

**计划改动文件**：`comic/server/internal/config/config.go`、`comic/server/cmd/api/main.go`、部署环境配置（实际部署文件路径待验证）、监控/运维说明。

**步骤**：迁移先行；代码以 `WX_PAY_ENABLED=false` 上线；fake 与生产 provider 明确隔离；先内部人员 0.01 元真测，再小流量固定价，观察通知积压、未支付超时、退款异常和每日账目；再按决议开启面议支付。关开关后不删支付账表；有交易事实时禁止执行 migration down。

**验收断言**：开关不可由客户端控制；关闭后无新真实下单；告警、查单补偿和回滚演练通过；灰度期间每笔成功/退款都能从 booking、payment、微信交易记录追溯。

## 4. 测试能力边界

| 可本地自动化（无商户号） | 必须人工真机/真商户号 |
|---|---|
| 订单金额换算为整数分、服务端金额权威性、零金额拒绝 | 真实小程序支付窗是否能拉起、支付人授权及 iOS/Android 表现 |
| 商户请求签名格式、调起参数签名（自生成测试密钥） | AppID/mchid 真实绑定与微信风控下的真实下单 |
| 原始 body 验签、AES-GCM 解密、错误密钥/改包拒绝 | 微信真实通知投递、真实重试节奏和证书/公钥配置兼容 |
| 通知重复/并发/乱序、支付与取消/关单对撞、事务幂等 | 退款资金是否实际退回及到账时效 |
| 退款状态机、超额退款拒绝、mock 账单解析与差异报告 | `/v3/security/echo`（需真实商户号）、真实 T+1 账单字段与日切 |
| 前端模拟收银台的成功/取消/失败交互 | 生产 HTTPS 回调可达性与商户平台配置 |

现有调查结论：微信支付 v2 沙箱已下线且未覆盖 JSAPI；微信支付 v3 没有公开沙箱。故 mock 只能证明本地实现逻辑，不能证明真实资金链路。

## 5. 决策清单

| 需要拍板 | 默认建议 | 未决影响 |
|---|---|---|
| 支付产品 | 普通商户直连小程序支付，使用 JSAPI 下单接口 `/v3/pay/transactions/jsapi`；不切 H5/Native | 主体若不具备商户资格，则不能进入真实交易阶段；待核实资质 |
| 收款与结算 | 首期平台商户统一收款，摄影师结算另行线下/运营处理并明确规则 | 平台是否为实际收款/售后主体、摄影师收入安排必须明确 |
| 付款对象 | 固定价及 coser 接受报价后的面议单全额预付；互勉免支付 | 定金、尾款、分账会扩大模型和产品流程，本期不建议 |
| 摄影师拒绝已支付订单 | 自动申请全额原路退款；退款处理中与预约取消分开显示 | 需要确认由谁承担退款手续费/通知用户及处理退款异常 |
| 用户/管理员取消退款 | 默认全额原路退款；按已发生服务阶段的比例规则作为待拍板事项 | 退款比例、时限和不可退条件必须在下单前展示 |
| 未支付超时 | 默认 30 分钟后查单、未支付则关单并取消释放档期 | 用户需确认是否与当前 H-8 pending 超时保持一致；H-8 的具体时长/定义待验证 |
| 对账 | 建议最小可用先人工每日核商户平台；完整方案在生产首发前接 T+1 交易账单，资金账单按财务需求 | 是否首发自动对账决定约 5-10 个开发人日增量及运营负担 |
| 支付开关 | 正式环境键统一为 `WX_PAY_ENABLED=false` 默认关闭；`PAYMENT_ENABLED` 仅作为需求别名不另设双键 | 防止双键配置不一致；实施前需要产品/运维确认配置名 |
| 当前价格单位 | 不做猜测；先从数据库样例确认，再规定一次性转换到整数分 | 未确认前不可开真实支付 |
| 账号映射 | 付款用户必须是当前登录用户、且使用同一 AppID 下 openid | 手机号账号与微信 openid 账号合并规则待确认 |

请决策者逐项回复：采用最小可用或完整方案；确认全额预付/拒绝及取消退款规则；确认支付超时与 H-8 关系；决定是否自动对账首发；提供商户资质状态及价格单位样例。

## 6. 明确不做

- 不做摄影师分账、平台抽佣结算或自动提现；普通商户收款不能暗中代替分账产品。
- 不做优惠券、满减、促销折扣或积分抵扣。
- 不做分期、定金/尾款多阶段扣款或自动扣款。
- 不把前端 `requestPayment` success 当作支付结果，不把 Redis 当资金事实来源。
- 不依赖已下线/不存在的微信支付沙箱，不在生产开放 mock 成功接口。
- 不在未确认金额单位、收款主体、退款规则前开启真实支付。
